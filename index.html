About

I'm an electrical engineering student at Stanford, currently working in the Arbabian Lab building a synchronized, single-computer ROS2 capture system that combines four Orbbec Femto Mega RGB-D cameras, a TI IWR6843ISK mmWave radar, and a Bosch SR250/STM32 UWB radar into one time-aligned rosbag pipeline for gait research. My work spans the full stack, from board-level firmware and network infrastructure to the synchronization architecture that keeps every sensor aligned to a shared clock.

I also build robots. In Stanford's CS 123 (AI-Enabled Robots) I worked a Pupper quadruped up from PD joint torque control through forward and inverse kinematics to a trotting gait, then replaced that hand-tuned gait with a walking policy trained by reinforcement learning in simulation and deployed onto the same hardware. Most recently I wrote the tool and prompt layer that lets a foundation model drive the robot, where the hard part is not the motion but making sure the model can only find out what actually happened through a channel that cannot lie to it.

Sensing and robotics are the same question for me: how do you get a system's picture of the world to match the world, and how do you know when it does not. I'm broadly interested in RF sensing, multimodal perception, robot control, and the systems-level work that makes any of it reliable outside a demo. I'm currently looking for Bay Area internships for Summer 2027, in EE hardware or robotics.

Research Interests

  • Robotics & control — legged locomotion, kinematics and gait generation, reinforcement learning for control, and sim-to-real transfer onto real hardware.
  • Embodied AI — giving foundation models a body: grounded tool interfaces, validation before a command reaches the motors, and honest reporting of robot state.
  • RF & radar sensing — FMCW mmWave radar signal processing, UWB ranging, and RF as a privacy-preserving alternative to vision-based sensing.
  • Multimodal sensor fusion — time-synchronizing heterogeneous sensors (cameras, radar, UWB) into a single coherent capture pipeline.
  • Systems & infrastructure — ROS2 architecture, embedded firmware (STM32), real-time control loops, and the networking/hardware layer sensing systems run on.
  • Gait & biomechanics — using synchronized sensor data to characterize normal and abnormal gait patterns for clinical and robotics applications.

Multimodal RF + RGB-D Gait Capture Platform

ROS2, Python/C++ · TI IWR6843ISK, Orbbec Femto Mega, STM32 · Active

A single-computer ROS2 system synchronizing four Orbbec Femto Mega RGB-D cameras, a TI IWR6843ISK mmWave radar, and a Bosch SR250/STM32 UWB radar into one time-aligned rosbag recording pipeline. Built the capture-gate synchronization architecture, diagnosed cross-subsystem frame loss (network, CPU, disk), and configured the dual-subnet sensor network (PoE camera/UWB switch plus a direct USB-Ethernet mmWave link). This is the active continuation of the work behind my earlier paper, extended to full multimodal, multi-camera synchronization.

Pupper: Quadruped Control Stack, Learned Gaits, and a Voice-Driven Agent

Stanford CS 123, AI-Enabled Robots · Python, ROS2, MuJoCo/mjlab, Raspberry Pi 5, Hailo accelerator · Fall 2026 · Active

Built the control stack for a Pupper quadruped from the joints up. It starts with PD torque control on a single leg joint over ROS2. Above that sits forward kinematics, written as per-leg transformation matrices, and an inverse kinematics solver that runs gradient descent on that forward model to turn a desired foot position into joint angles. Then swing trajectory generation and a trotting gait, tuned by hand through timer frequency, stride length and stance position until the robot could cover a ten-foot course instead of falling over halfway down it.

The next stage replaced the hand-tuned gait with a learned one. I trained a velocity-tracking walking policy with reinforcement learning in mjlab, a MuJoCo-based environment, using domain randomization so the policy would survive the move onto real hardware, then pulled the trained checkpoint from Weights and Biases down onto the robot. Building both controllers for the same chassis is the useful part. The comparison shows where a model of a robot stops predicting the robot. Perception runs on-device in the same loop: a YOLOv8n-seg segmentation model on a Hailo accelerator drives a proportional person-following controller at 10 Hz, with range estimated from the bottom edge of the bounding box since the camera carries no depth sensor.

The current lab puts a foundation model in charge. Gemini Live hears the person, sees through the camera and decides what to do, while the gait controllers and trained policies remain the only things that actually move. I wrote the layer between them: the motion tools the model can call (straight moves, turns in place, arcs), the validation that rejects a command before it reaches the motors if it breaks a speed, duration or distance limit, the follow-mode rule, and trick playback. I also wrote the system prompt that governs how the model is allowed to report what happened. That part mattered more than I expected. A language model will happily announce that it is walking when the queue actually refused the command, so the rules have to be explicit: call the tool before talking, treat a queued reply as waiting rather than finished, never claim a motion the robot did not accept, and read the robot's real status instead of guessing. Giving a model a body turns out to be mostly an exercise in making sure the only channel it learns through cannot lie to it.

Autonomous Mechatronic Balancer

Python, Computer Vision, Servo Control · Mentor: Wei Cai · Jun 2025 – Sep 2025

A closed-loop control system combining a CMOS camera and servo actuator to stabilize a ping-pong ball on a pivoting lever arm in real time. Built a real-time Python computer vision/ML pipeline to track ball position frame-by-frame and minimize control loop latency, with hardware-in-the-loop testing and iterative calibration validated through weekly quantitative performance reports.
